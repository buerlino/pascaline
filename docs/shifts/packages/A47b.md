**Why:** (phase-1 `fa52380`) a branch is checked and audited against phase-1 as it was when its run started: phase-1 is merged into the branch only for a resumed branch or `--no-worker` (`merge_phase1`, `scripts/pipeline.sh:522`, called at :546). 2. **The queue:** after the worker, and after each fix round, the run takes `integ` (up to 7200 s, the wait logged), then runs `merge_phase1` (its resolve round as today), `select_engine`, the checks, the behaviour diff and the audit; on APPROVED it merges and promotes the engine, then releases. A failed check or a FIX releases `integ`; the fix round runs outside; the run queues again (at most two fix rounds, as today). A branch with its own engine key builds that engine before it queues when it can.
3. **Lock order:** `integ` before `host-cpu`, everywhere; nothing that holds host-cpu waits for `integ`. Stated in the script header.
4. **Starts:** the package and the brief are read from phase-1's commit (`git show phase-1:<path>`), so a start never needs the worktree clean; `npm ci` in the phase-1 worktree and the node_modules copy run under `integ`.
